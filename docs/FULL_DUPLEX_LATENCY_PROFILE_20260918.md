# TFD-STAR 全双工 Demo 延迟与误打断诊断

> 日期：2026-09-18  
> 诊断对象：`audio_duplex` 公网演示链路  
> 状态：本地修复、远端部署、编译预热、localhost/公网/SSH直连探针均已完成；尚待用户进行真实麦克风复测。

## 1. 结论先行

这次体验问题不是单一的“4080 算力不足”，而是三个问题叠加：

1. **确定性的误打断协议缺陷**：后端在正常回答结束时发送 `listen`，前端却把所有 `listen` 都当成用户插话，清空尚未播放完的语音。因此会出现“用户没说话，它自己把自己打断”。
2. **固定播放缓冲过大**：浏览器原先收到首块音频后再等待 2000 ms 才播放。用户观测到 `TTFS=1692 ms` 时，仅这两项相加，理论可感知开口时间就约为 `1692 + 2000 = 3692 ms`，尚未计入输入块边界和网络抖动。
3. **公网中继延迟与生成余量不足叠加**：已测公网 RTT 约 352–366 ms；模型一片约 800–1100 ms，而每片代表约 1000 ms 音频。800 ms 尚可实时，但只有约 200 ms 余量；超过 1000 ms 时播放器就会逐渐“断粮”，表现为一卡一卡、`Ahead` 变红。

因此，第一阶段应先部署本次协议与客户端修复。只有在**服务器本机链路**下仍长期 `Infer > 1000 ms`，才值得为算力升级 GPU。

## 3. 端到端延迟预算

当前链路为：

`Realtek 麦克风 → 浏览器采集/AEC → 1 秒 Float32 音频块 → Gradio WebSocket 中继 → Gateway → Worker → Python duplex_prefill/generate → 音频块返回 → 浏览器抗抖缓冲 → 播放`

### 3.1 用户说完到系统开口

粗略预算为：

`等待当前输入块封口（平均约 0.5 秒，最差接近 1 秒） + 模型首次开口 TTFS + 公网传输/调度 + 播放缓冲`

- 旧配置：`0–1000 + 1692 + 网络/调度 + 2000 ms`
- 本次配置：公网入口保留1200ms；localhost/SSH直连自动使用400ms。

仅降低固定播放缓冲就减少约 800 ms。它不能消除模型和公网延迟，但会直接改善“说完很久才开口”的体感。

### 3.2 用户说“停”到真正静音

旧链路必须等待：当前 1 秒麦克风块封口、上传、服务端收到 `force_listen`、下行确认，再由浏览器停止已经排队的音频，因而可能达到数秒。

新链路在浏览器侧执行：

1. AEC 后的麦克风信号进入本地轻量 VAD；
2. 检测到持续人声后立即 `audioPlayer.stopAll()`；
3. 下一块上行音频只携带一次 `force_listen`，让远端状态随后追上；
4. 设置 1200 ms 冷却，避免一次插话反复触发。

因此“听觉上的停止”不再等待公网往返。目标是从秒级降到本地检测窗口的约 110–190 ms，再加浏览器调度开销。

## 4. 根因详解

### 4.1 自己打断自己：协议原因

后端存在三类“切回聆听”：

- `turn_end`：正常回答完成；
- `model_listen`：模型主动决定继续听；
- `force_listen`：用户按钮或本地插话检测要求立即停止并听。

旧协议没有传 `reason`。前端只要收到 `listen`，就会清空播放器。V2 音频增量消息又没有携带可靠的 `end_of_turn` 状态，导致正常 `turn_end` 也很容易被视作打断，尚在缓冲区的结尾语音被截掉。

修复后，只有 `force_listen`、明确的 `barge_in`、手动强制聆听，或刚发生过本地 VAD 插话时才清空音频；`turn_end` 与 `model_listen` 只结束逻辑轮次，不砍掉已经排队的尾音。

### 4.2 一卡一卡：实时系数接近 1

每个模型输出单元约对应 1 秒音频。若一片推理耗时：

- 800 ms：实时系数约 0.8，有约 200 ms 余量；
- 1000 ms：刚好踩线，没有抖动余量；
- 1144 ms：每片落后约 144 ms，连续多片后 `Ahead` 必然下降并产生断点。

所以 `Infer=800 ms` 本身不是故障，却说明当前 4080 已接近实时边界。公网的突发到达会进一步吃掉余量。

### 4.3 为什么暂不把块改为 250 ms

浏览器当前上传的是 16 kHz 单声道 Float32，模型原生时间单元约 1000/1035 ms。后端对每个 WebSocket 消息执行一次 `prefill + generate`。如果只把浏览器消息切成 250 ms：

- 首块会被补零到模型要求的长度；
- 后续短块可能被判断为音频不足；
- 仍然触发 generate，反而增加调度和协议开销；
- 模型的生成粒度并不会自动变成 250 ms。

跨轮 KV 与流式音频状态本来就在复用。真正做到 250 ms 增量生成需要修改模型的时间步、音频编码器缓存和训练/推理契约，并重新验证质量，不能仅改一个 `chunk_seconds` 配置。

### 4.4 为什么 Opus/WebRTC 不是第一刀

当前并非 PCM16，而是 Float32 PCM：

- 上行 16 kHz × 1 声道 × 32 bit，原始约 512 kbps，Base64 后约 683 kbps；
- 下行 24 kHz × 1 声道 × 32 bit，原始约 768 kbps，Base64 后约 1 Mbps。

PCM16 只能把当前载荷约减半，不是 8 倍。Opus 约 32 kbps 确实能显著瘦身，WebRTC 也更适合媒体抖动与弱网，但服务器当前直接消费 Float32；迁移需要浏览器编码、服务端解码、WebRTC 信令、抖动缓冲和重连策略，是一项独立的传输层改造。现有带宽并未显示为主要瓶颈，先修协议和公网路径更划算。

## 6. GPU 与部署建议

### 是否马上升级 GPU

**暂时不要因为这次现象直接升级。** 误打断、2 秒固定缓冲和 350 ms 公网 RTT 都不是更大显存能解决的。

部署本次修复后，用两个维度做决定：

1. **服务器本机测试**：若热态 `Infer` 长期低于 900 ms，4080 可以继续用；
2. **服务器本机仍长期超过 1000 ms**：才说明算力余量确实不足，应升级计算性能。

如升级，优先 H100/H800 这一档，而不是仅看“80 GB”。A100 80GB 的显存更大，但本项目当前只用约 22 GB，容量不是主要矛盾；需要的是更强 Tensor Core、显存带宽和更稳定的实时余量。

### FP8 判断

FP8 可能将 9B 权重占用从约 23 GB 降到约 12 GB，并释放并行模块空间，但：

- 当前显存尚有约 11 GB 余量；
- 自定义多模态全双工模型不一定能无修改接入通用 FP8；
- 需要 Transformer Engine 或适配的量化内核，并验证语音质量与状态缓存精度；
- 内存减半不等于端到端延迟减半。

因此 FP8 属于第二阶段实验，不应替代本次确定性修复。

### 原生 duplex_server 判断

当前实际链路已经走原生双流推理：浏览器 `/v1/realtime?mode=audio` → Gateway → Worker → Python Backend → `duplex_prefill/generate`。并不是半双工接口外包一层 WebSocket。因此“切原生 duplex_server”并非尚未完成的开关；真正可优化的是传输路径、模型时间粒度和推理内核。

## 8. 指标释义

- **会话状态（State）**：连接生命周期，如空闲、连接、运行、暂停和结束。
- **会话标识（SID）**：用于把浏览器现象和服务端日志对应起来的 session ID。
- **对话状态（Mode/Model）**：模型当前正在聆听还是回答。
- **音频分片（Chunks）**：已处理的输入流式单元数量；当前每片约 1 秒。
- **上下文占用（KV）**：KV Cache 中保留的上下文 token 数，并非 GPU 利用率。
- **视觉输入（Vision）**：音频模式无关，已在新界面隐藏。
- **单片推理（Infer）**：服务器处理一个流式单元的墙钟时间；低于 1000 ms 才有持续实时余量。
- **首次开口（TTFS）**：从模型进入聆听到首次决定说话，不包含完整浏览器播放缓冲。
- **播放缓冲（PDelay）**：浏览器收到首块后主动预存的时间；越大越稳，开口越慢。
- **音频余量（Ahead）**：已经排队、尚未播放的音频时长；接近 0 或变红意味着即将断粮。
- **累计补偿（Shift）**：为初始缓冲与播放断点累计平移时间轴的总量，不等同于单次网络延迟。
- **链路漂移（Drift）**：当前结果到达延迟相对首块的变化；持续变大说明链路逐渐落后。

### 10.4 Gradio 公网中继

- 连续 HTTP `/status` 请求：约978–1627ms；
- 聆听片：模型 Infer 约83–95ms，但公网墙钟约0.77–1.15秒；

Base64 Float32 音频块经过该中继时出现明显吞吐与排队问题。它正是“模型已经算完，用户仍过几秒才听见”的主要来源。

### 10.5 SSH 直连入口

在用户电脑上建立 `127.0.0.1:18006 → SSH → 远端127.0.0.1:8006` 的持久转发后：

- HTTP 重复请求：约116–133ms；
- 聆听片完整墙钟：151–222ms；
- 语音片完整墙钟：856–946ms；
- 语音片模型 Infer：约675–767ms；
- 热态 p90墙钟约906ms，最大946ms。

该入口已经回到实时范围，且 localhost 在浏览器中属于可信来源，可正常请求麦克风。当前最优测试地址为 `http://127.0.0.1:18006/audio_duplex`。

### 10.6 最终显卡决策

当前不建议升级显卡：

- 本机语音 Infer 已低于1秒；
- Gradio 把约0.7秒模型生成放大为2–4秒，升级GPU无法消除这部分；
- 直连后端到端已低于1秒，证明首要优化项是传输。

只有在后续增加更重模型、视频分支、并发会话，或直连条件下语音 Infer p90 再次超过1000ms时，才建议换H100/H800。
