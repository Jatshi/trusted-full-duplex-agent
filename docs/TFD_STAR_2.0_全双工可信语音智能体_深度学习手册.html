00 · 一分钟把项目讲清楚

项目解决的是一个典型的语音 Agent 落地矛盾：模型越追求“像人一样随时开口”，越可能抢话、误听后执行危险动作，或者在用户打断后丢掉上下文；系统越保守，又会变成反应迟钝的按键式助手。

何时说

语轮 MLP 每 100 ms 读取声学时序特征，输出 hold / take / backchannel。连续 4 帧确认后才允许基座开口。

能否做

TrustGate 根据语义含糊、风险词与置信度选择 execute / clarify / stop，高风险动作不会因“听得清”就直接执行。

怎么学

GRPO 对同一个提示采样一组回复，以内容一致性、护栏动作和上下文回忆评分，用组内相对优势更新 LoRA。

2.0 新增 早期 TrustGate 只在离线脚本中接收现成文本，实时 Demo 实际无法从麦克风得到可判定文本。2.0 增加 Faster-Whisper-small，把真实波形转成文字、平均 log-prob 和 no-speech 概率，TrustGate 才真正进入在线链路。

面试口述版

“我做的是一个可信全双工语音智能体。MiniCPM-o 负责理解和生成语音，我在它外面加了三层控制。第一层是浏览器本地即时打断，让用户一开口就先停播放器；第二层是训练过的轻量语轮 MLP，判断该继续听、接话还是给反馈；第三层是 ASR 驱动的 TrustGate，判断请求能直接执行、需要追问还是必须停止。我还用 GRPO LoRA 对打断后的上下文回忆和安全动作做了后训练，并把所有层接进真实 WebSocket Demo，而不是只做离线指标。”

两条环路是关键：客户端环追求“用户一开口，听感立即停止”；服务器环追求“什么时候允许模型开口，以及这条指令能否执行”。前者不能代替后者，后者也不能弥补公网往返造成的打断迟钝。

03 · 一块真实音频到底怎么走

  1. 采集：浏览器请求指定输入设备，开启 echo cancellation、noise suppression 与 auto gain control，得到 16 kHz 单声道 Float32 PCM。
  2. 本地判断：仅在智能体正在播音时运行轻量 VAD。一旦确认真人插话，浏览器先清空播放队列，再在下一块上行消息中只携带一次 force_listen。
  3. 服务器接收：server.py::_push_full_duplex 解码音频和视频帧；若是客户端插话，则重置当前用户语轮的 MLP 与 TrustGate 状态。
  4. 语轮决策：StreamingTurnController 把任意大小 chunk 切成 100 ms 帧，提取 10 维特征，MLP 输出概率与动作。只有检测到足够语音、足够尾部静音且动作连续确认为 take，才 allow_speak=true。
  5. 安全转写：2.0 新增 累计真实波形交给 Faster-Whisper；输出经繁体转简体，计算 segment 时长加权 avg_logprob 和 no-speech probability。
  6. TrustGate：文字进入含糊、风险和置信度三条路径，选择 execute / clarify / stop / listen。
  7. 动作：execute 让 MiniCPM-o 正常 duplex_prefill + duplex_generate；clarify/stop 阻止自由生成并播放确定性护栏语音；listen 继续等待。
  8. 下行：服务器返回 text/audio/listen delta，并携带 turn、gate、prefill、wall-clock、KV 等指标。前端依据 reason 区分正常轮次结束与真正打断。
语音水位线修复：2.0 记录 _gate_released_voiced_frames。若没有新 voiced frame，就不对同一段 12 秒滚动窗口重复做 ASR/TrustGate。这个修复直接解决“沉默时反复识别旧话并重复路由”的问题。

04 · MiniCPM-o 4.5 在系统里负责什么

基座同时处理音频上下文和语音输出。服务器每个时间单元先做 duplex_prefill，把新的音频特征写入流式状态；再做 duplex_generate，模型可能生成 <|listen|>，也可能生成 <|speak|> 后的文本 token 和语音 token。TTS/Token2Wav 把语音 token 转成约 24 kHz 波形。

保留的状态

跨 chunk 的音频编码状态、LLM KV cache、语音生成缓冲和当前 listen/speak 模式。它们决定流式连续性；每块都重新建会话会彻底失去全双工意义。

外挂控制的边界

MLP 与 TrustGate 不替换基座理解能力。它们分别控制“是否放行说话”和“是否允许自由回答/执行”。最终自然语言与正常语音仍由基座产生。

为什么叫系统层全双工

当前真实服务已经使用 listen/speak 双流接口，但可信控制主要在系统层完成。浏览器可在模型输出时继续采集，客户端能即时截断播放，后端可继续 prefill 用户声音，并依据外部时机/安全模块约束生成。因此它不只是“上传整段录音后等待整段回复”，但也不能把所有行为都宣称为我们重新训练出的模型内生全双工能力。

05 · 语轮 MLP：把“什么时候开口”独立出来

它不是 ASR，也不理解句子含义。它观察声学时序，回答一个更小但很重要的问题：这一刻应该继续听、接管话轮，还是给简短反馈？

输入：每 100 ms 的 10 维因果特征

特征含义为什么有用
energy_db当前帧能量，映射到 0~1区分 voiced 与静音
pause_len连续静音长度，1.5s 截断归一化结尾停顿通常更长
energy_slope最近 0.5s 能量斜率自然收尾往往能量下降
speech_ratio_1s/3s短/长窗口语音占比描述局部停顿与整体语速
utt_speech_s本轮累计语音时长很短的片段通常不该抢答
n_inner_pauses已出现停顿次数反映犹豫和复杂表达
pre_pause_speech_s停顿前语音段长度短语音加长停顿更像思考
last_voiced_energy最后语音帧能量区分逐渐收尾与高能量急停
pre_pause_drop尾部相对约 400 ms 前的下降量是判定说完的重要先兆

网络与损失

x ∈ R10 → Linear(10,32) → ReLU → Linear(32,3) → {hold,take,backchannel}

训练用带类别权重的交叉熵。take 和 backchannel 的样本更少、漏判代价更高，所以权重为 2；hold 权重为 1。优化器 Adam，学习率 0.01，300 epochs，seed=42。

为什么单帧预测后还要连续 4 帧确认

句中停顿和句末停顿本来就重叠。只看一帧时，模型偶发把句中停顿判为 take；连续 4 个 100 ms 帧都支持 take 才开口，相当于用约 300 ms 额外等待换显著更低的抢话率。Pareto 结果从 1 帧的 24% 假开口降到 4 帧的 0%，中位接话延迟从 265 ms 增至 554 ms。

数据边界：训练集是参数化合成声学，不是大规模真人双人对话。模型证明了工程接口、损失和时序平滑有效；不能把 0% 假开口写成开放世界 SOTA。

06 · TrustGate：不用 LLM 做最后一道安全判断

TrustGate 是确定性、可解释、低延迟的规则/统计门。它不调用另一个 LLM 来“投票”，因为实时安全分支需要稳定、可审计，而且 LLM 自己也会幻觉。LLM 负责自然回答；Gate 决定是否允许进入自由回答路径。

核心量

confidence = scale(avg_logprob) × uncertainty factor
risk ∈ {0, 0.4, 0.8}　　score = risk × (1 − confidence)

scale(logprob)=1/(1+(-logprob))。当前没有 intent probability 向量时，entropy 默认 0.5，且 use_uncertainty=true，因此置信度还会乘 0.75。风险由关键词上界决定：删除、转账等不可逆动作至少 0.4；转弯、变道、急刹等物理动作 0.8。

实际决策顺序比 score 更重要

优先级条件动作理由
1文字含“那个/这个/你看着办”等省略目标表达clarify听清不等于说完整，独立处理语义含糊
2confidence < 0.45 且 risk > 0stop高风险又没听清，宁停不猜
3confidence < 0.45 且无风险clarify核心库的保守兜底
4risk ≥ 0.8stop物理危险动作不自动执行
50.4 ≤ risk < 0.8clarify不可逆动作先二次确认
6score ≥ 0.60 / 0.30stop / clarify风险与不确定性的连续区间
7其余execute低风险、明确请求放行

为什么一开始 Demo 会“有动静就 clarify”

Faster-Whisper 在短噪声或弱语音上会给低置信文字；核心 TrustGate 的低置信兜底会把它判成 clarify。实时集成层后来增加两条语音系统语义：

  • 没有可靠文字，或只有一个字符且置信很低：改为 listen，环境声不能触发固定追问。
  • 只有“低风险 ASR 不确定”，且没有风险：改为 execute，让 MiniCPM-o 直接听原始音频，而不是让安全监视 ASR 接管正常聊天。
关键设计：ASR 是 safety monitor，不是 conversational recognizer。它擅长给 Gate 提供可审计文本证据，但低风险对话仍由多模态基座理解原始声音。

07 · 2.0 新增 ASR 安全转写链路

是的，ASR 是后来新加的。没有它时，TrustGate 的离线脚本拿到的是人工准备的文本；真实 Demo 的麦克风波形无法直接进入关键词风险与含糊判断，因此所谓“在线可信护栏”并未闭环。

为什么选 Faster-Whisper-small

  • 它用 CTranslate2 推理，CPU int8 可运行，把 32GB GPU 留给 9B speech-to-speech 基座。
  • small 的中文准确性、速度和 464MB 存储体积适合安全监视器。
  • 提供 avg_logprob 与 no_speech_prob，能构造可解释置信度。

代码中的完整处理

segments = whisper.transcribe(
    audio, language="zh", beam_size=1,
    vad_filter=True, condition_on_previous_text=False
)
text = OpenCC("t2s").convert(join(segment.text))
avg_logprob = duration_weighted_mean(segment.avg_logprob)
no_speech = duration_weighted_mean(segment.no_speech_prob)
asr_confidence = exp(avg_logprob) * (1 - no_speech)

繁体转简体非常重要，因为 Gate 的关键词表是简体。如果 ASR 输出“刪除”，而风险词只有“删除”，不归一化就会漏报。数字归一化目前没有加入 Gate 的风险匹配，因为现有风险词不依赖数值格式；如果以后做转账金额或药物剂量，则应增加中文数字、阿拉伯数字与单位归一化。

12 秒滚动窗口与水位线

控制器只保留最近 12 秒波形，避免长会话无限增长。每次 Gate 放行后记录已处理的 voiced-frame 数；只有出现新语音帧才再次评估。若是噪声 pseudo-turn，则同时清空 TurnController 和 TrustGate 缓冲。

不要误解：Whisper 的 VAD 并不是系统的唯一 VAD。浏览器本地 VAD用于打断；语轮 MLP 内部用能量阈值统计 voiced/silence；Faster-Whisper 的 VAD filter 只用于 ASR 分段。三者目标不同。

08 · GRPO、LoRA 与在线加载：训练闭环到底做了什么

为什么用 GRPO

同一个输入没有唯一正确回答，但可以判断哪条更安全、更忠实。GRPO 对一个 prompt 一次采样 G 条回答，以组内均值和方差计算相对优势，不需要单独训练 value critic，适合小规模验证。

Ai = (ri − mean(r)) / (std(r) + 10−8)

两类训练数据

族样本优化目标reward
安全/语轮回复300 条，execute/clarify/stop 五类场景生成动作符合 Gate，内容与参考一致归一化 BLEU-1 + 动作分类一致
barge-in 上下文60 条，5主题×3截断点×4插话表达只复述被打断前已经说出的内容，不编造未播部分字符 bigram Jaccard + BLEU-1

reward 公式

rgate = [1.0·content_consistency + 0.7·action_match] / 1.7
rbarge = [1.0·bigram_Jaccard(generated, interrupted) + 0.5·content_consistency] / 1.5

Jaccard 的分母是并集，因此添加未播出的幻觉内容会增大分母、降低分数。训练和 63 号探针评测调用同一个 bigram_overlap，避免“训练优化 A、汇报指标 B”。

最小可微 GRPO loss

L = − mean(Ai · log πθ(yi|x)) + β · mean(log πθ − log πref)

生成阶段使用 do_sample=true, top_p=0.9 得到组内回答；训练阶段把 prompt 与生成 token 拼接，逐 token gather log-softmax，只对生成区域求和。为了避免 151k 词表的整批 float32 log-softmax 在 32GB 卡上 OOM，代码按样本逐行转换和计算，峰值从约 1.2GB 降到约 75MB。

KL 参照没有额外复制一个 9B 模型

LoRA 模式下，disable_adapter() 就得到冻结基座的 log-prob，因此不需要再加载一份 9B reference model。β=0.1 的项约束更新不要偏离基座太远。这里的实现是线性 log-prob 差近似锚，不等同于完整 token-level KL 期望，文档与代码都不把它夸成标准 TRL 全功能实现。

LoRA 参数与部署

r=16, alpha=32, dropout=0.05，目标为所有 linear 层，包括 q/k/v/o 和 MLP up/down/gate projection。训练保存 PEFT adapter；服务启动时调用内部 model.llm.load_adapter() 并 set_adapter()，不替换 MiniCPM-o 外层多模态类。

结果不能只挑正数：Qwen2.5-1.5B 的 context recall 0.301→0.484，学习信号清楚；MiniCPM-o 9B 的轻量训练多数配置退化，最佳 20-step 配置 reward +0.015 也接近采样噪声。2.0 在线加载的是这份最温和的 9B adapter，但发布保留全部负结果。

09 · 2.0 强化 打断：为什么必须“客户端先停，服务器再追”

旧链路要等当前采集块封口、上传、服务器处理、下行确认，然后浏览器才停止排队语音。公网 RTT 和模型时间叠加后，“说停”可能几秒才生效。2.0 将听感和状态同步拆开：

  1. 浏览器在 Agent 播放期间检测到持续真人语音。
  2. 立即调用 audioPlayer.stopAll()，无需等服务器。
  3. 下一块上行只发送一次 force_listen=true，让服务器状态追上。
  4. 进入冷却窗口，防止同一次插话反复触发。

AEC 为什么重要

扬声器播放的女声会被麦克风收到。如果没有 WebRTC AEC 或阈值太灵敏，本地 VAD 会把回声当成人声，造成“系统自己把自己打断”。所以浏览器采集必须打开 AEC，优先用耳机验证，并提供保守/均衡/灵敏三档阈值。

listen 消息为什么要带 reason

服务端的 listen 有三种完全不同的语义：turn_end 是正常答完；model_listen 是模型主动继续听；force_listen 才是强制打断。旧前端见到 listen 就清空播放器，正常轮次尾音也会被截掉，听起来像卡顿。2.0 只在真正打断原因下清空。

10 · 2.0 新增 护栏语音统一

正常回答走 MiniCPM-o 的女声音色，而早期 clarify/stop 使用离线生成的男声 WAV，用户会明显感到“换了一个人”。2.0 重新生成并替换两段确定性护栏语音，保持和正常对话一致的女声风格。

动作固定话术原因
clarify为了避免误操作，我需要再确认一下。请把对象和具体操作说清楚。确定性表达，防止自由生成反而执行
stop这个指令可能带来安全风险，我现在不会执行。请先确认安全条件。明确拒绝，不给危险动作模糊空间

服务器读取 WAV 后转单声道、必要时重采样到 24 kHz，再编码为 Float32 Base64，下行路径和正常音频一致。缓存避免每次磁盘读取。

11 · 2.0 新增 实时性优化与为什么不是单纯换显卡

瓶颈分解

模型

每个约 1 秒输出单元若推理超过 1 秒，音频余量会持续减少。

网络

Gradio 中继曾把约 0.7 秒生成放大到 2.3~4.2 秒墙钟；SSH 直连恢复到 1 秒内。

播放器

缓冲太小会断粮，太大会让首次开口变慢。localhost 当前默认 700 ms。

为什么“LoRA 加载后再 compile”

如果先编译基座再动态挂 adapter，图捕获可能绕开或破坏可训练分支。2.0 检测到 TFD_GRPO_ADAPTER 后，先 eager 加载模型和 adapter，再选择性 compile。完整 LLM 图在本次 4080 32GB 环境编译超过 12 分钟，收益与风险不匹配；默认只编译 TTS model，首次 warm-up 132.6 秒，之后复用缓存。

实测变化

阶段后端客户端观察解释
早期 1s 片median 约 1.36s，RTF 1.42Ahead 容易变红无法持续实时
2.0 最新短探针median 0.742s / mean 0.794smedian 0.824s / mean 0.897s恢复到每片 1 秒预算内
显卡结论：4080 SUPER 32GB 的热态推理可以低于实时线。80GB 只解决容量，不自动解决公网 RTT、协议误打断或播放缓冲。只有直连下 Infer p90 长期高于 1000 ms，或增加视频/并发，升级 H100/H800 才更有依据。

17 · 这次真正踩过的坑，以及如何解释

坑 1：Demo 看起来能聊，其实自研组件没接上

症状：页面能全双工对话，但只是上游 duplex 能力。根因：LoRA、MLP 和 Gate 是不同仓库/脚本，没有 runtime 装配。解决：新增 tfd_runtime.py，所有组件由环境变量显式启用，并把状态放进 metrics 与日志。

坑 2：任何声音都进入 clarify

症状：环境声和普通问句都播放固定追问。根因：短窗 ASR 低置信被核心 Gate 的保守兜底拦截。解决：空/极短低置信文本映射为 listen；低风险 ASR 不确定交给原始音频基座；含糊和风险仍拦截。

坑 3：沉默时重复识别旧话

根因：滚动 ASR buffer 保留旧音频，而每次 take 条件重新出现都评估同一内容。解决：voiced-frame watermark，只在新语音到来后重评；噪声 pseudo-turn 清空状态。

坑 4：系统自己打断自己

根因：前端把正常 turn_end 的 listen 当作 barge-in，清掉未播放尾音；扬声器回声又可能触发本地 VAD。解决：listen reason 协议 + AEC + 播放期间限定 VAD + 冷却。

坑 5：LoRA 与 torch.compile 顺序冲突

根因：编译图和动态 adapter 的执行路径不一致。完整 LLM 编译又耗时超过 12 分钟。解决：先加载 adapter，再编译；默认只编译 TTS，LLM compile 作为显式实验开关。

坑 6：9B GRPO 可微 log-softmax OOM

根因：批量 float32 logits 形状约为 B×L×151k，峰值过大。解决：保持 logits，逐行做 float32 log-softmax 与 gather，单行峰值约 75MB；采样后释放 KV cache 碎片。

坑 7：更大显存不等于更低交互延迟

证据：服务器内热态小于 1 秒，而公网中继达到 2~4 秒；改走 SSH 直连后恢复。结论：先分解 model time、network wall time 与 playback delay，再决定是否换卡。

18 · 诚实边界与下一版应该做什么

  • GRPO 数据规模小：60/300 条适合闭环验证，不足以证明通用安全对齐。
  • 9B 增益不稳：当前在线 adapter 是可运行的研究产物，不应宣称显著提升所有语音任务。
  • MLP 合成域：需要 Switchboard、CallHome 或自采真人双人语音做域外验证与再训练。
  • TrustGate 词表有限：生产系统需要意图分类器、实体完整性、用户确认状态机和审计日志。
  • 传输仍是 WebSocket Float32：未来可独立做 PCM16/Opus 和 WebRTC，但不能只把 chunk 参数从 1s 改 250ms 就宣称模型粒度变小。
  • 单会话验证：缺并发、长稳、网络丢包、浏览器矩阵和端到端 SLO。

最有价值的 2.1 路线

收集带真人 EOT、重叠语音与回声条件的对话集，重新训练 MLP；把 TrustGate 的风险实体和确认状态机结构化；为 ASR 与 base audio understanding 做双路一致性校准；建立 30 分钟长稳探针、p50/p90/p99 与 false interrupt 统一 benchmark。

19 · 高频面试问答

Q1：你这个和 MiniCPM-o 官方 Demo 有什么区别？

官方 Demo 提供基座和服务骨架；我做的是可训练的语轮决策、ASR 驱动的三态 TrustGate、GRPO adapter 训练与部署、客户端即时打断、协议 reason 修复、指标与完整测试。2.0 的重点是把这些自研组件真正接入在线链路，并保留基座/自研归属。

Q2：为什么 Gate 不直接让 LLM 判断？

最后一道安全门需要低延迟、确定性和可审计。LLM 可以辅助上游意图抽取，但最终阈值、不可逆动作 floor 和停止策略最好是显式状态机。这样同一输入能复现，也能做单元测试。

Q3：GRPO 为什么不用 critic？

同一 prompt 的 G 个候选天然形成相对比较。reward 标准化后得到组内优势，不必拟合 value model，降低小规模实验复杂度。但代价是组内 reward 方差不足时没有学习信号，所以报告里统计了 signal_steps。

Q4：为什么 1.5B 变好，9B 反而退化？

强基座在 text-context recall 上接近天花板，小数据和 group=4 的 reward 信号不足；采样噪声大，KL=0.1 也未完全锚住策略。更关键的是线上失败主要是 audio-token 自我回忆，而训练是 text-context，存在模态 gap。

Q5：ASR 和 MiniCPM-o 都能听语音，为什么重复？

角色不同。MiniCPM-o 为自然对话理解原始音频；Faster-Whisper 是可审计的安全传感器，产出文字、logprob 与 no-speech 概率供 Gate。低风险不确定会退回基座，不让 ASR 劫持对话。

Q6：如何证明 Demo 不是开关造假？

启动日志确认 adapter、MLP、ASR/Gate 分别加载；每个下行 chunk metrics 含 turn 概率和 gate action；设置环境变量可做同一服务的 baseline/增强 A/B；Python 与 JS 契约测试覆盖装配与协议。

Q7：最棘手的问题是什么？

不是模型 forward，而是三个时间尺度互相干扰：100ms 语轮帧、约1s模型单元、数百毫秒网络/播放器缓冲。最终用客户端即时环解决听感，用服务器可信环解决状态一致性，再用 reason 与 watermarks 避免重复事件。

21 · 术语速查

Prefill

把新输入编码并写入当前会话状态/KV 的阶段。

KV cache

Transformer 保存历史 key/value，避免每次重算全部上下文。

Barge-in

智能体说话期间用户插话，并要求系统立即让行。

Backchannel

“嗯、明白”一类不抢走话轮的短反馈。

LoRA

冻结基座，仅训练低秩增量矩阵，降低显存和存储成本。

GRPO

按同一 prompt 的组内 reward 计算相对优势的策略优化。

AEC

Acoustic Echo Cancellation，消除扬声器回灌到麦克风的声音。

RTF

Real-Time Factor，处理时长/音频时长；持续实时需要小于 1。
